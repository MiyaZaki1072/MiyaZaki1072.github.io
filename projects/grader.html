Kit2Code Grader

A self-hosted practice grader for old competitive-programming contest problems: read the statement, submit, and get the score the original contest would have given.

Code ›

Why I built it

Kit2Code's contests are judged on our own CMS, the contest system the IOI runs on. The grader gives those problems, and other old contest problems, a place to be practised: anyone can open one, submit C, C++ or Python, and see per-test and per-subtask results scored exactly the way CMS v1.5 scored the original contest. It runs on the same small home server as our CMS.

What it had to do

  • Score like CMS. Old problems must get the same score they got in the contest, subtasks included.
  • Take CMS tasks as they are. Problems already packaged for CMS have to import without being rewritten by hand.
  • Run untrusted code safely, on a server that is also running a live CMS with a sandbox of its own.
  • Thai first. Thai is the default language, with English one click away.
  • Fit a small machine. One home server, little memory, no cloud bill.

What I chose

  • Python only. Django 5.2 with server-rendered pages and htmx, and a Python judge worker. One language, no Node build step, less memory on a shared server.
  • One web image, two roles. The same Django image runs as the public practice site and as the admin site. The public role's URL configuration doesn't contain the admin pages or the judge's internal API at all, so a bug on the public site can't reach them. The edge (Caddy) adds a zone header on top, and a session made in one role is thrown away in the other.
  • CMS's scoring, re-implemented. Sum and GroupMin follow CMS v1.5.1, tests in the same order. Where CMS would crash or quietly mis-score (an empty subtask, an outcome outside 0–1), the grader refuses the problem at import with a clear message instead.
  • An importer for CMS's Italian task format: names, limits, statements, subtasks, graders, checkers and file input/output. A checker has to come as source, not as a binary built for some other machine.
  • Two sandboxes that never collide. isolate 2.7 is built from a pinned commit and given its own cgroup root, user ids and box ids, apart from CMS's. The worker container drops every capability and adds back only the eight isolate needs, and every program starts through a small launcher that installs a seccomp filter of its own. The worker has no internet, no route to the database and no database password.
  • Postgres as the queue. No Redis. The worker asks the admin site for jobs and holds each one on a 60-second lease, so if it dies its jobs simply come back; two workers can never take the same job.
  • Sign-in with Google only, through one locked-down exit on the edge. The grader never asks for an email, and secrets live in files, never in environment variables or in git.
  • Docker Compose, installed as one app on the home server and reached through a Cloudflare tunnel, so the router has no open ports.

Where it is

Early development. Students can sign in, read problems, submit and watch their results arrive live, with problem lists, a ranking and profiles. Admins set the site up from a one-time link and import, validate and publish problems, pause grading, check the judge and request backups from the admin site.

Next

Split the public site into a JSON API and a separate React front end, then run monthly rated contests on CMS 1.5.1, with a live public scoreboard and Codeforces-style ratings.
